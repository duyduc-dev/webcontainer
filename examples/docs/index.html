Architecture

Three workers, one process table.

Everything runs inside the browser tab. The kernel never touches the network or disk directly — it routes; the FS and process workers do the actual work, each in its own thread.

worker.0
Kernel
Routes host-page requests, owns the process table, relays cross-process networking, services the sync fs/exec bridges when cross-origin isolated.

worker.1
FS
In-memory virtual filesystem. Reachable async over postMessage, or synchronously via a SharedArrayBuffer + Atomics bridge from a guest process's own thread.

Quickstart

No await, no backend.

bootDWC() returns real, usable handles immediately — every call queues behind the kernel's boot handshake on its own.

import { bootDWC } from "@dwc/core";
 
const dwc = bootDWC(); // synchronous
 
await dwc.fs.mkdir("/project", { recursive: true });
await dwc.fs.writeFile("/project/server.js", source);
 
const proc = await dwc.process.spawn("/project/server.js");
dwc.addEventListener("listen", ({ port }) => {
  iframe.src = dwc.preview.url(port); // live preview
});
Status

Pre-1.0, actively built in the open.

Everything here is what's actually true today, not a roadmap dressed up as a feature list.

Works today

  • Real npm install against the live registry, including npm itself
  • Real CJS + native ESM module loading, live bindings
  • 32 real Node builtins behind require()
  • Guest HTTP servers, previewed live in an iframe
  • A synchronous SharedArrayBuffer bridge for fs.*Sync and execFileSync

Known gaps

  • No native binary execution — no esbuild/native addons, no wasi yet
  • Guest HTTP responses are fully buffered, text-only
  • No HMR — WebSocket upgrades aren't interceptable by a Service Worker
  • dwc.shell.exec() doesn't expose a real exit code
